# ai.kr.24 블로그 글쓰기 규칙 (2026-10-16 대표님 직접 지시)

아래 규칙은 모든 글에 강제 적용된다. 하나라도 어기면 그 글은 발행하지 않는다.

## 1. 실용적이어야 한다

- 독자가 읽고 바로 써먹을 수 있는 정보만 쓴다.
- 단계별 실제 명령, 복사-붙여넣기 가능한 예시, 바로 따라 할 수 있는 절차를 담는다.
- "설정 예시는 다음과 같습니다"라고 쓰고 예시를 빼먹는 것은 금지. 약속한 예시는 반드시 넣는다.
- 배경 설명이 필요해도 최소한으로만 하고, 읽는 사람의 다음 행동으로 연결되지 않는 문단은 삭제한다.

## 2. 사실만 작성한다

- 검증되지 않은 내용은 쓰지 않는다. 테스트로 확인한 명령, 공식 문서에서 확인한 동작, 실측 데이터만 사용한다.
- 추측·"아마도"·출처 없는 주장은 금지. 구체적인 숫자(예: 토큰 수)를 쓸 때는 어디서 확인한 값인지 근거가 있어야 한다.
- 검증할 수 없는 항목은 빈 칸이나 "미확인"으로 두지 말고 항목 자체를 뺀다.
- "업계의 관심이 집중되고 있습니다", "파장을 일으킬 것으로 예상됩니다" 같은 근거 없는 일반론은 금지.

## 3. 슬롭이 아니라 진짜 도움이 되는 정보만 쓴다

- 분량 채우기, 뻔한 일반론 나열, 진부한 표현은 금지한다.
- 모든 문단에 "이 정보가 독자에게 무엇을 도와주는가"를 자문한다. 답이 없으면 지운다.
- 정보가 적으면 짧은 글이 정답이다 — 길게 늘리지 않는다.
- "향후 전망" 같은 추측 섹션은 실측 데이터가 없으면 쓰지 않는다.

## 4. 실측 규칙 (모델 글)

- 테스트 없이 웹 리서치만으로 발행하지 않는다.
- 모델 글에는 `## N. ai.kr.24 실측 결과` 섹션을 넣는다. 검증일·검증 방법·모델 ID·결과를 적는다.
- 사용법은 실제 테스트한 명령만 쓴다.
- `:free` 접미사의 중요성을 반드시 언급한다. 접미사를 떼면 유료 항목으로 연결될 수 있다.

## 5. 톤·형식 규칙

- 모든 문장은 `~입니다`체로 끝낸다. `~다`로 끝내지 않는다.
- 본문에 `# 제목`을 쓰지 않는다. (제목은 TITLE: 줄에 한 번만)
- 제목에 대괄호 수식어를 붙이지 않는다. (`[충격]` 등 금지)
- 'AI'를 '아이'로 음역하지 않는다.
- 구어체·은어를 쓰지 않는다. '돈' 대신 '비용'.
- 자사 표기는 `ai.kr.24`(쓰레드 계정) 와 `aikorea24.kr`(사이트) 두 가지만 쓴다. 축약형 `aik24` 는 금지한다.
- 크루 내부 용어를 쓰지 않는다. (독자가 모르는 말 금지)
- 중국어(한자)·이모티콘 사용 금지.
- 본문 첫 단락에서 '이번 글에서는', '살펴보겠습니다' 등 메타 도입문 금지. 핵심 내용으로 바로 시작한다.

# 부록: 발행 게이트 대응 항목 (스킬 `aik24-blog-writing` §1·§3·§4 발췌 — 2026-10-17 AIK24-BLOG-01)

위 1~5 규칙에 더해, 생성 단계에서 아래를 지킨다. 발행 게이트(`scripts/emdash_precheck.py`)가 기계적으로 검사하며, 미달이면 발행이 차단된다(exit 3).

## A. 구조

- 본문에 `#`(H1)을 쓰지 않는다. 제목은 `TITLE:` 줄에 한 번만 쓴다.
- 도입 문단(첫 3~4문장): ① 무엇인지 ② 언제 공개됐고 규모가 어떤지(사실) ③ 이 글이 답하는 것(독자가 얻는 것).
- 소제목은 `## N. 동작 — 결과/약속` 형태로 번호를 붙인다. 예: `## 1. 설치 — 3분이면 끝납니다`
- 마지막에 **문자 그대로 `## 마무리 — …`** 로 시작하는 소제목을 하나 둔다. **없으면 발행하지 않는다.**
- 마무리에 넣을 내용은 글 종류를 따른다. ① 설치·사용법 글: "오늘 30분 안에 할 3단계" 실행 체크리스트. ② 모델·도구 소개 글: **어디에 쓰면 좋은지**(작업 유형별로 어울리는 자리) → 쓰면 안 되는 자리 → 아직 검증하지 않은 항목 순서. 소개 글에서는 설치 절차를 다시 나열하지 않는다.
- 사용자 프롬프트가 "**요약** 섹션"을 요구하면, 별도 섹션을 하나 더 만들지 말고 그 섹션을 `## 마무리 — 요약` 형태로 합쳐 쓴다.

## B. 게이트 검사 항목 (미달 시 발행 금지)

- 본문 H1 없음
- `## 마무리` 소제목 있음
- 외부 링크 3개 이상 (출처·키 발급·설치 페이지를 인라인 링크로)
- 표 1개 이상 — 마크다운 표만 쓴다. **HTML 금지**(태그가 텍스트로 노출된다)
- 코드펜스(```) 짝이 맞음
- 본문 3,000자 이상 — 사실을 더 모아서 채운다. 말로 늘리지 않는다
- 내부 용어 0개 — 프로젝트 내부 도구명·스크립트 경로·사내 키 이름·장애 복구·배포 이야기 금지

## C. 사실 서술

- 시점 의존 수치(컨텍스트 한도·가격·버전)는 **출처와 "YYYY년 M월 D일 기준"을 함께** 쓴다. 출처가 없으면 그 수치를 쓰지 않는다.
- 서술 주체는 독자다. 키 등록은 설정 파일 손편집이 아니라 UI 경로로 쓴다 — 예: TUI 에서 `/connect` → 제공자 검색 → API key 붙여넣기.
- 확인하지 못한 설치 명령·서브커맨드는 빼거나 "확인 필요"로 남긴다. 추측해서 쓰면 회귀다.
- "어떻게 하는가"는 실행 가능한 표로: ① 어디서 받는지(URL) ② 어디에 넣는지(환경변수명) ③ 예시 코드를 갖춘다.
- 무료/유료를 사실대로 구분한다. 무료라고 뭉뚱그리지 않는다.
- 실측 수치는 표본·분모·비율을 같이 쓴다 (예: "623세션 중 564건(90.5%) 무료").
